02

The proof that counts

A CPU that passes a testbench is a claim. A CPU that runs a program you didn't write specifically for it is evidence.

A bare-metal RISC-V GCC cross-toolchain was built from source — not installed from a package manager — targeting this specific core. A compiled C bubble-sort program was then run end to end on the CPU, from reset through program completion, with correct results at the end. That closes the loop from "the RTL simulates correctly" to "this is a computer that runs software."

Formal verification, and catching itself lying twice

Beyond running software, three specific properties were formally verified against independent reference computations.

Applied lesson

Three vacuous proofs were caught and fixed across this portfolio before trusting these results — directly applying what Project 2's async FIFO taught: a proof that reports success while checking a structurally disconnected property is worse than no proof at all. Auditing every "PASS" for vacuousness is now a standing step, not an afterthought.

What these proofs cannot see

The first two checks above re-derive the design’s own logic. The branch one compares branch_taken against a reference computed in the bind file, from the same ALU result, with the same case statement. It catches a typo or a refactor mistake. It cannot catch a misreading of the specification, because both sides would be wrong together. Calling it “independent” was generous — and the next section is how that became obvious.

04

Proving the ISA, not my own opinion of it

Block-level proofs check the design against itself. riscv-formal checks it against the RISC-V specification — and found something four passing proofs and a working C program had all missed.

The core was instrumented with an RVFI trace port reporting every cycle exactly what retired. The harness instantiates the CPU with no memory attached — instruction and data words are free inputs, so the solver explores every response memory could give.

Bug found

Fourteen checks failed on the first run, all on assert(spec_trap == trap). RV32I requires a trap on a misaligned branch or jump target — the core had none. Adding it fixed loads, stores and jumps, but every branch still failed.

The counterexample: a PC already misaligned, executing a branch not taken. The next PC is pc + 4, inheriting the misalignment — and the spec raises the trap on a branch’s computed target whether or not it is taken. The condition was gated on branch_taken; it needed branch. One word.

No directed test would construct that state, and the bind-file proof could not see it: it re-derives the same condition from the same signals.

Applied lesson · third time

Debug signals tapped through hierarchical dot-paths reported zero at every timestep — after flattening they resolve to dump-time constants, with no tool warning. The tell was an impossible pair: pc and pc_plus4 both zero, when pc_plus4 is a continuous assign of pc + 4. Fix: observe through real module ports, never dot-paths into a flattened design.

Scope: proofs run under RISCV_FORMAL_ALIGNED_MEM, the same assumption the reference picorv32 configuration uses. No CSRs, no interrupts, no compressed instructions.

05

Differential testing, and measuring what the fuzzer reaches

The interesting result was not the clean run — it was what measuring the generator revealed.

A direct instruction injection harness on Verilator answers every fetch from a queue indexed by retirement order rather than PC. No memory image, no linker script. The same stream runs against a Python model written from the specification, traces are diffed field by field, and a delta-debugging shrinker minimises any mismatch.

The finding that mattered

A fuzzer that finds no bugs is indistinguishable from one that checks nothing — the vacuous-proof trap, one level up. So a known bug was planted in the reference (SRA behaving as SRL). It was not caught.

Measuring the generator explained why: across 6,000 generated instructions there were zero SRA instructions with a negative operand. Registers start at zero and accumulate small immediates, so SRA/SRL, SLT/SLTU and BLT/BLTU were exercised syntactically while the behaviour distinguishing them was never reached.

A LUI/ADDI prelude seeding wide values, plus biased register selection, fixed it. The planted bug was then caught and shrunk from 52 instructions to 4. Only then did a clean run mean anything.

Honest limitation: the reference shares an author with the RTL, so a shared misreading would go undetected. It was written from the spec rather than the RTL to reduce that, and riscv-formal covers conformance independently. The contribution here is the injection and shrinking infrastructure, not the reference.
