The reconstruction

A method rebuilt from prose

Weingarten, Datta, Kole & Drechsler (DATE 2024; Table III from PolyMiR, NANOARCH 2023) verify a RISC-V processor instruction-by-instruction using Binary Decision Diagrams. Their in-house tools — PSIM, SYMSIM, RMG — were never published. Each was reconstructed from the method description using open tools, and one of the substitutions is itself an argument: the paper's ternary simulation with pinned opcodes and unknown data bits is constant propagation, expressed in different tooling.

Self-correction

Two of my own explanations, disproved

The most credible part of this project is not the numbers that matched — it's the equivalence machinery turning around and falsifying two explanations I had already written down. Both corrections are proofs, not revisions of opinion.

Earlier claim — adder architecture explains the ADD gap

Canonicity makes that impossible

An ROBDD is unique for a given function and variable order. So a Kogge-Stone parallel-prefix network and a ripple-carry chain — sharing no internal structure — must produce byte-identical BDDs. Measured directly: they do. The 17% gap to the paper's 1327 cannot be architectural, for any adder that computes addition.

circuit (ripple-carry) : 3, 5, 8, 11, … 95 sum = 1553 reference (Kogge-Stone) : 3, 5, 8, 11, … 95 sum = 1553 identical
Earlier claim — the exact AND/XOR matches validate the counting metric

The paper's counts measure the construction path, not the function

As functions, 32-bit bitwise AND and XOR have identical BDDs — three nodes per output bit. Yet building XOR by walking its 96-gate AIG yields 161, while AND yields 97. Same function class, same order, different numbers: the metric counts intermediate BDDs created during construction. Any convention reproducing the paper's 97-vs-161 distinction is measuring that artefact, because at the function level there is no distinction to measure.

AND as function : 96 sum · 97 manager XOR as function : 96 sum · 97 manager identical BDDs XOR via its AIG : 161 manager construction-path artefact
Reproducibility finding

A node count without its variable order is not a result

The same circuit, the same tool, the same function — separated only by the order in which variables are declared. And a second trap underneath it: py-aiger iterates inputs in hash order, which changes per process, so identical code produced 6036 nodes on one run and 6585 on the next until PYTHONHASHSEED=0 was pinned. The consequence generalises well beyond this project: any published BDD node count that omits its variable ordering is unreproducible — including Table III.

Reproduce it

Two environments, one file between them

Yosys lives in a nix-shell; the BDD stack lives in a Python venv. They never share an interpreter — the synthesiser writes AIGER to disk and Python reads it back. 

# extract all ten sub-circuits (Yosys, inside the nix-shell)
nix-shell --run "./scripts/run_all.sh extract"

# validate the reference model itself — 4,096 assignments per op
python3 scripts/test_rmg.py 6

# prove all ten equivalences
./scripts/run_all.sh check
